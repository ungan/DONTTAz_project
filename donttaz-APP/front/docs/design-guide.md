# Front Design Guide

## 1. 문서 목적

이 문서는 현재 `front` 코드 기준으로 프론트 디자인 일관성을 유지하기 위한 협업 가이드다.

이 문서의 목적은 아래와 같다.

- 새 화면을 만들 때 기존 협업자 스타일을 깨지 않도록 한다.
- 나중에 협업자가 디자인을 수정할 때 수정 지점을 줄인다.
- 사람뿐 아니라 CLI가 작업할 때도 같은 기준을 참고할 수 있게 한다.

이 문서는 완성된 디자인 시스템 명세서가 아니다.
현재 코드베이스에서 실제로 보이는 패턴을 기준으로 정리한 실무용 가이드다.

아직 코드에 없는 미래 구조나 예정 규칙은 이 문서에 미리 확정해서 적지 않는다.
새 구조나 공용 규칙이 실제로 프로젝트에 반영되면 그 시점에 이 문서를 업데이트한다.

## 2. 이 문서를 언제 참고하는지

아래 상황에서는 먼저 이 문서를 확인한다.

- 새 화면을 만들기 전
- 기존 화면 UI를 수정하기 전
- 버튼, 입력창, 링크 같은 공용 UI를 수정하기 전
- CLI에게 프론트 작업을 요청하기 전
- 코드 리뷰에서 화면 스타일 일관성을 확인할 때

## 3. 현재 프로젝트 디자인 스타일 요약

현재 프로젝트에서 읽히는 디자인 방향은 아래와 같다.

- 전체 톤은 라이트 테마 중심이다.
- 대표 색상은 `Primary (#5AA9FF)` 중심이다.
- 흰 배경과 회색 보조 텍스트를 자주 사용한다.
- 스플래시처럼 브랜드가 드러나는 화면은 캐릭터와 큰 타이틀을 강조한다.
- 일반 폼 화면은 단순하고 깔끔한 세로 흐름을 유지한다.
- 여백은 크게, 정렬은 단순하게, 화면 구조는 복잡하지 않게 가져간다.

현재 코드에서 보이는 대표 패턴은 아래와 같다.

- 기본 수평 여백은 `16`을 자주 사용한다.
- 자주 쓰는 간격은 `8`, `16`, `48`이다.
- 본문 텍스트 크기는 `16` 기준이 많다.
- 공용 입력 높이는 `52`다.
- 버튼과 입력은 둥근 모서리를 사용한다.
- 브랜드 타이틀은 `Chewy` 폰트를 사용한다.

## 4. 화면 구현 체크리스트

### 4.1 화면 구조

- 라우트 파일은 `app`에 최소한으로 두고, 실제 화면 UI는 `pages`에 둔다.
- 화면 안에서 기능 단위로 나눌 수 있으면 `features`로 분리한다.
- 버튼, 링크, 인풋처럼 재사용 가능한 요소는 먼저 `shared/ui`에 있는지 확인하고 우선 사용한다.
- 한 파일에 화면 전체 로직과 세부 UI를 모두 넣지 않는다.
- 스타일은 가능하면 화면 또는 섹션 단위로 분리하고 `StyleSheet.create`를 사용한다.

### 4.2 레이아웃

- 기본 화면은 복잡한 배치보다 단순한 세로 흐름을 우선한다.
- 전체 여백은 현재 코드 기준 `paddingHorizontal: 16`을 기본값으로 생각한다.
- 요소 사이 간격은 `gap: 8`, `16`, `48`처럼 이미 쓰이는 값 안에서 맞춘다.
- 화면 폭은 무조건 꽉 채우기보다 필요한 경우 적절한 폭 제한을 둔다.
- 정렬은 중앙 정렬 또는 단순 정렬을 우선하고, 과한 비대칭 배치는 피한다.

### 4.3 색상

- 대표 색상은 `Primary (#5AA9FF)`를 우선 기준으로 사용한다.
- 배경은 우선 흰색 또는 브랜드 컬러 중심으로 맞춘다.
- 회색 텍스트와 보조색은 기존 화면 톤과 크게 다르지 않게 맞춘다.
- 새 화면에서 임의의 강한 포인트 컬러를 추가하지 않는다.
- 색상을 직접 하드코딩해야 한다면 기존 화면과 공용 컴포넌트 색상과 충돌하지 않는지 먼저 확인한다.

### 4.4 타이포

- 브랜드 타이틀이 아닌 일반 텍스트는 단정하고 읽기 쉬운 톤으로 유지한다.
- 본문, 입력, 링크는 현재 코드에서 자주 쓰는 `16px` 기준을 우선 참고한다.
- 큰 제목은 스플래시나 로그인처럼 필요한 화면에만 사용한다.
- 브랜드성 강한 텍스트만 `Chewy`처럼 개성 있는 폰트를 사용한다.
- 새로운 폰트 스타일을 추가할 때는 기존 화면과 섞였을 때 이질감이 없는지 먼저 확인한다.

### 4.5 공용 컴포넌트 사용

- 버튼이 필요하면 먼저 `shared/ui/button.tsx`를 사용할 수 있는지 확인한다.
- 텍스트 링크는 `shared/ui/text-link.tsx`를 우선 사용한다.
- 일반 입력 UI는 `shared/ui/custom-input.tsx`로 통일 가능한지 먼저 검토한다.
- 화면마다 버튼, 링크, 입력을 새로 만들기 전에 기존 공용 컴포넌트를 확장하는 방식이 가능한지 본다.
- 공용 컴포넌트를 수정할 때는 한 화면만 좋아지는지보다 다른 화면도 함께 자연스러운지 확인한다.

### 4.6 스타일 작성 방식

- 스타일 값은 JSX 안에 직접 넣기보다 `styles`로 분리한다.
- 반복되는 값은 여러 파일에서 제각각 다르게 쓰지 않도록 주의한다.
- 같은 의미의 요소는 비슷한 `radius`, `padding`, `fontSize`를 유지한다.
- 화면 하나만 맞추는 예외 스타일을 남발하지 않는다.
- TODO 상태의 화면이라도 스타일 구조는 임시로 섞어 쓰지 않는다.

### 4.7 새 화면 만들 때 최종 확인

- 이 화면이 기존 `splash`, `login`과 나란히 있어도 이질감이 없는가
- 여백, 폰트 크기, 버튼 모양이 기존 톤과 크게 다르지 않은가
- 공용 컴포넌트로 대체 가능한 부분을 새로 만들지 않았는가
- 스타일이 `app / pages / features / shared` 구조를 깨고 있지 않은가
- 협업자가 나중에 색상이나 버튼 스타일을 바꿀 때 수정 지점이 너무 많아지지 않는가

## 5. 수정 용이성 원칙

### 5.1 바뀔 가능성이 높은 값은 한곳에 모은다

- 대표 색상, 배경색, 텍스트 색, 보더 색처럼 자주 바뀔 수 있는 값은 공용 상수로 관리한다.
- 현재는 `Primary`만 확실하므로 앞으로는 `Background`, `TextPrimary`, `TextSecondary`, `Border`, `Danger` 같은 토큰 확장을 고려한다.
- 여러 화면에서 반복되는 숫자값도 나중에 공통 `spacing` 또는 `radius`로 묶을 수 있게 의식하고 사용한다.

### 5.2 공용 컴포넌트를 먼저 고치면 전체가 같이 바뀌게 만든다

- 버튼 스타일을 바꾸고 싶을 때 화면마다 수정하지 않도록 버튼은 가능한 `shared/ui/button.tsx`를 중심으로 쓴다.
- 링크 텍스트도 `shared/ui/text-link.tsx` 기준으로 맞춘다.
- 입력창 스타일은 화면 전용 구현보다 `shared/ui/custom-input.tsx` 기준으로 맞추는 방향을 우선한다.
- 공용 컴포넌트가 부족하면 새 화면 안에서 임시 복붙하지 말고 공용 컴포넌트를 확장할 수 있는지 먼저 본다.

### 5.3 하드코딩은 화면 전용 예외일 때만 둔다

- 색상 하드코딩은 최소화한다.
- 같은 의미의 여백, `borderRadius`, 높이를 화면마다 다르게 직접 쓰지 않는다.
- 폰트 크기와 색상을 JSX 근처에서 반복해서 새로 정하지 않는다.
- 새 코드부터는 공통화 우선 원칙을 따른다.

### 5.4 화면은 조합하고 스타일 규칙은 공용으로 끌어올린다

- `pages`는 화면 조합 역할에 가깝게 유지한다.
- `features`는 기능 단위 UI를 담당하게 한다.
- 재사용 가능성이 생기는 순간 `shared`로 올리는 기준을 둔다.
- 화면 파일이 길어질수록 세부 스타일을 더 들고 있기보다 공용 규칙을 참조하는 방향으로 간다.

### 5.5 브랜드 규칙과 일반 UI 규칙을 분리한다

- 브랜드성 요소는 로고, 마스코트, 스플래시 타이틀처럼 한정된 곳에서만 강하게 쓴다.
- 일반 버튼, 입력창, 본문 텍스트는 최대한 차분하고 반복 가능한 형태로 유지한다.
- 이렇게 분리해야 나중에 브랜딩만 바꾸거나 일반 UI만 정리할 때 충돌이 적다.

## 6. 파일 구조 원칙

현재 프론트 구조는 아래 역할 분리를 기준으로 유지한다.

- `app`: 라우트 진입 파일과 레이아웃만 둔다.
- `pages`: 실제 페이지 단위 UI를 둔다.
- `features`: 기능 단위 UI와 모델을 둔다.
- `shared`: 공용 UI, 상수, 훅, 에셋을 둔다.

추가 원칙은 아래와 같다.

- 라우트는 얇게 유지하고 실제 구현은 `pages` 또는 `features`에서 처리한다.
- 재사용 가능한 UI가 생기면 `shared`로 올린다.
- 화면 하나에서만 쓰는 UI는 섣불리 `shared`로 올리지 않는다.
- 공용화 타이밍은 "두 군데 이상에서 비슷한 규칙이 반복될 때"를 기준으로 본다.

### 6.1 폴더별 책임 빠른 판단 기준

- `app`: 화면 경로 연결, 레이아웃 설정, 라우트 진입만 담당한다.
- `pages`: 실제 화면 단위의 배치와 조합을 담당한다.
- `features`: 특정 기능과 직접 연결된 UI 또는 로직을 둔다.
- `shared`: 여러 화면이나 기능에서 함께 쓸 수 있는 가장 공통적인 요소를 둔다.

아래처럼 판단하면 된다.

- "이 파일은 라우트 연결만 하면 되는가?" -> `app`
- "이 파일은 하나의 화면 전체를 구성하는가?" -> `pages`
- "이 파일은 로그인 같은 특정 기능에 속하는가?" -> `features`
- "이 파일은 다른 화면에서도 반복해서 쓸 가능성이 높은가?" -> `shared`

### 6.2 공개 방식 원칙

- 각 폴더는 가능하면 `index.ts`를 통해 외부에 공개할 것을 정리한다.
- 다른 파일에서 내부 구현 경로를 깊게 직접 import하기보다 폴더의 공개 경로를 우선 사용한다.
- 이렇게 해야 내부 구조가 바뀌어도 import 경로 수정 범위를 줄일 수 있다.

예시:

```ts
import { LoginPage } from '@/pages/login';
import { LoginFormSection } from '@/features/auth';
```

직접 내부 경로를 깊게 타는 import는 필요할 때만 사용한다.

## 7. 공용 수정 지점

디자인 수정 시 먼저 확인할 주요 파일은 아래와 같다.

- 색상과 테마 기준: `shared/constants/theme.ts`
- 버튼 기준: `shared/ui/button.tsx`
- 링크 기준: `shared/ui/text-link.tsx`
- 입력창 기준: `shared/ui/custom-input.tsx`
- 전체 라우트 구조: `app/*`
- 화면 레이아웃 예시: `pages/login`, `pages/splash`

이 파일들을 먼저 수정하면 화면별 개별 수정 범위를 줄일 수 있다.

## 8. 현재 프로젝트의 부족한 점과 주의사항

현재 프로젝트는 디자인 시스템이 완전히 정리된 상태는 아니다.
아래 사항을 염두에 두고 작업한다.

- `Primary` 외 색상 토큰이 충분히 정리되지 않았다.
- 다크모드 관련 구조는 있으나 실제 화면 반영은 거의 라이트 기준이다.
- `Chewy`는 로드되지만 `Roboto` 사용 기준은 아직 불완전하다.
- 로그인 화면은 공용 입력 컴포넌트와 완전히 통일되어 있지 않다.
- 일부 화면은 아직 TODO 상태라 현재 규칙이 앞으로 바뀔 수 있다.

따라서 새 작업은 아래 방향을 우선한다.

- 기존 화면과 이질감이 없을 것
- 공용화가 가능한 부분은 공용화 방향으로 작성할 것
- 한 화면만을 위한 독자 규칙을 먼저 확정하지 않을 것

## 9. CLI 및 협업용 작업 규칙

사람이나 CLI가 프론트 작업을 할 때 아래 원칙을 우선한다.

- 새 화면 구현 전 이 문서를 먼저 참고한다.
- 기존 공용 컴포넌트를 먼저 사용하고, 꼭 필요할 때만 새 컴포넌트를 만든다.
- 새로운 대표 색상이나 독자 스타일 규칙을 임의로 추가하지 않는다.
- 재사용 가능성이 보이면 `shared`로 분리한다.
- JSX 안에 인라인 스타일을 많이 넣지 않는다.
- 한 화면만 맞는 예외 스타일을 만들지 않는다.
- 디자인 변경이 필요하면 먼저 공용 수정 지점을 확인한 뒤 작업한다.

### 9.1 새 화면 추가 최소 절차

새 화면을 추가할 때는 아래 순서를 기본으로 한다.

1. `app`에 라우트 파일을 만든다.
2. `pages`에 실제 화면 컴포넌트를 만든다.
3. 기능 단위로 분리할 부분이 있으면 `features`로 나눈다.
4. 버튼, 입력창, 링크 등은 먼저 `shared/ui` 공용 컴포넌트 사용 가능 여부를 확인한다.
5. 스타일이 기존 화면과 어울리는지 `splash`, `login` 기준으로 비교한다.

예시 흐름:

```tsx
// app/example.tsx
import { ExamplePage } from '@/pages/example';

export default ExamplePage;
```

```tsx
// pages/example/index.ts
export { ExamplePage } from './ui/example-page';
```

### 9.2 현재 문서 업데이트 원칙

- 이 문서는 현재 코드에 실제로 존재하는 구조와 규칙만 기록한다.
- 아직 도입되지 않은 `widgets`, `entities`, 상태관리, mock 구조 같은 미래 설계는 여기서 미리 확정하지 않는다.
- 새 공용 컴포넌트, 새 레이어, 새 디자인 토큰이 실제로 도입되면 그때 문서에 추가한다.
- 문서가 코드보다 앞서가지 않도록 유지하는 것을 우선 원칙으로 한다.

## 10. 추후 개선 후보

프로젝트가 진행되면 아래 항목을 순차적으로 정리하는 것을 권장한다.

- 색상 토큰 확장
- 공용 `spacing` 체계 정리
- 공용 `radius` 체계 정리
- 타이포 스케일 정리
- 입력창 패턴 통일
- 실제 폰트 로드 정책 통일
- 다크모드 대응 범위 결정
