# RabbitMQ 비동기 알림 시스템 도입 근거 및 기술 가이드

우리 서비스에서 외부 웹훅(Discord, Mattermost) 알림 전송에 RabbitMQ를 도입한 이유와 관련 핵심 기술 개념을 설명합니다.

## 1. 비동기 처리 (Asynchronous Processing) 도입 이유

### 응답성 (Latency) 개선
- **문제:** 외부 웹훅 API 호출은 네트워크 지연이나 상대 서버 상태에 따라 1~2초 이상 소요될 수 있습니다.
- **해결:** 사용자는 금고 거래(입/출금) 버튼을 누른 즉시 응답을 받아야 합니다. 알림은 "이벤트"로 발행하고 백그라운드에서 처리함으로써 사용자 응답 속도를 **1000ms -> 10ms 단위**로 단축했습니다.

### 장애 격리 (Fault Tolerance)
- **문제:** 디스코드나 메터모스트 서버가 일시적으로 다운되면, 동기 방식에서는 우리 서비스의 입/출금 로직까지 함께 실패하거나 타임아웃이 발생합니다.
- **해결:** 알림 서버의 상태와 상관없이 우리 서비스의 핵심 비즈니스 로직은 독립적으로 수행됩니다.

## 2. 핵심 기술 개념 상세 설명

### 🔄 지수 백오프 (Exponential Backoff)
재시도 시 대기 시간을 기하급수적으로 늘려가는 전략입니다.
- **왜 사용하는가?** 외부 서버가 부하를 견디지 못해 장애가 난 경우, 즉시 여러 번 재시도하면 서버 상태를 더욱 악화시킬 수 있습니다.
- **작동 방식:** 
    1. 첫 실패 후 1초 대기
    2. 두 번째 실패 후 2초 대기
    3. 세 번째 실패 후 4초 대기... (2의 n제곱)
- **장점:** 네트워크 혼잡을 방지하고 대상 서버가 회복할 시간을 충분히 줍니다.

### 🛣️ 유연한 라우팅 (Exchange & Routing Key)
RabbitMQ의 메시지 전달 모델은 게시자(Publisher)가 큐(Queue)로 직접 메시지를 보내지 않고 **익스체인지(Exchange)**로 보냅니다.

- **익스체인지 (Exchange):** 메시지를 받아 어떤 큐로 보낼지 결정하는 우체국 같은 역할을 합니다.
    - **Direct:** 라우팅 키가 정확히 일치하는 큐로 전달.
    - **Topic:** 와일드카드(`#`, `*`) 패턴을 사용하여 유연하게 전달.
    - **Fanout:** 연결된 모든 큐에 메시지 복사본 전달 (브로드캐스트).
- **라우팅 키 (Routing Key):** 메시지에 붙는 '꼬리표' 혹은 '주소'입니다. Exchange는 이 키를 보고 어떤 큐(예: `penalty-queue`)에 넣을지 판단합니다.
- **이점:** 향후 알림 플랫폼이 추가되거나(예: 이메일, 카카오톡), 특정 알림만 다른 서버에서 처리하고 싶을 때 **코드 수정 없이** 설정만으로 확장 가능합니다.

## 4. 동기 vs 비동기: 지연 시간의 진실 (Latency Comparison)

벤치마크 테스트에서 두 방식 모두 **가상 지연 1초(Thread.sleep)**를 포함하고 있습니다. 하지만 결과는 판이하게 다릅니다.

| 항목 | 동기 방식 (Sync) | 비동기 방식 (RabbitMQ) |
| :--- | :--- | :--- |
| **실제 작업량** | 1초 (외부 API 호출) | 1초 (외부 API 호출) |
| **누가 기다리는가?** | **사용자 (HTTP 스레드)** | **백그라운드 (RabbitMQ 컨슈머)** |
| **Swagger 응답 시간** | **1,000ms+** | **10ms~50ms** |

### 이 데이터가 의미하는 것
비동기 처리라고 해서 1초 걸리는 작업이 0.1초 만에 끝나는 '마법'이 일어나는 것은 아닙니다. 하지만 **"사용자가 그 1초를 기다리지 않고 다른 일을 할 수 있게 해주는 것"**이 비동기 처리의 진정한 가치입니다. 사용자는 즉시 입금 완료 화면을 보고, 알림은 1초 뒤에 백그라운드에서 조용히 전달됩니다.
