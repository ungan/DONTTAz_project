# RabbitMQ 비동기 알림 시스템 도입 근거 및 기술 가이드

우리 서비스에서 외부 웹훅(Discord, Mattermost) 알림 전송에 RabbitMQ를 도입한 이유와 관련 핵심 기술 개념을 설명합니다.

## 1. 메시지 큐 기술 스택 선정 근거 (RabbitMQ vs Others)

단순히 비동기 처리를 하는 것 이상으로, 왜 **RabbitMQ**를 선택했는지 타 기술 스택과 비교하여 설명합니다.

### 📊 기술 스택 비교표

| 비교 항목 | Spring @Async (In-memory) | Redis (Pub/Sub) | **RabbitMQ** | Apache Kafka |
| :--- | :--- | :--- | :--- | :--- |
| **메시지 영속성** | **없음** (서버 재시작 시 유실) | 낮음 (Fire & Forget) | **높음** (디스크 저장 가능) | 매우 높음 (로그 저장소) |
| **재시도 지원** | 수동 구현 필요 | 어려움 | **강력함** (DLX, 백오프 지원) | 가능 (복잡한 구현 필요) |
| **라우팅 유연성** | 낮음 | 매우 낮음 | **매우 높음** (Exchange/Key) | 보통 (Topic 방식) |
| **관리 복잡도** | 없음 | 낮음 | **보통** | 매우 높음 (클러스터 운영) |
| **주사용처** | 간단한 일회성 작업 | 실시간 채팅, 가벼운 캐싱 | **신뢰성 있는 작업 전달** | 대용량 로그/스트림 처리 |

### 💡 왜 우리 프로젝트에 RabbitMQ인가?
1. **신뢰성 있는 알림 전달:** 사용자의 소중한 입/출금 알림은 유실되어서는 안 됩니다. `@Async`는 서버 중단 시 메시지가 사라지지만, RabbitMQ는 서버가 다시 뜰 때까지 메시지를 안전하게 보관합니다.
2. **복잡한 라우팅 불필요:** Kafka는 대규모 스트림 처리에 최적화되어 우리 수준의 알림 서비스에는 오버스펙(Overkill)이며 운영 부담이 큽니다. 반면 RabbitMQ는 설정이 직관적이면서도 강력한 라우팅을 지원합니다.
3. **유연한 확장성:** 현재 Discord, Mattermost 외에 향후 SMS, 이메일 등이 추가될 때 브로드캐스트(Fanout)나 패턴(Topic) 매칭을 통해 기존 코드 수정 없이 알림 채널을 확장하기 가장 좋은 구조입니다.

## 2. 핵심 기술 개념 상세 설명

### 🔄 지수 백오프 (Exponential Backoff)
재시도 시 대기 시간을 기하급수적으로 늘려가는 전략입니다.
- **왜 사용하는가?** 외부 서버가 부하를 견디지 못해 장애가 난 경우, 즉시 여러 번 재시도하면 서버 상태를 더욱 악화시킬 수 있습니다.
- **작동 방식:** 
    1. 첫 실패 후 1초 대기
    2. 두 번째 실패 후 2초 대기
    3. 세 번째 실패 후 4초 대기... (2의 n제곱)
- **장점:** 네트워크 혼잡을 방지하고 대상 서버가 회복할 시간을 충분히 줍니다.

### 🛣️ 유연한 라우팅 (Exchange & Routing Key)
RabbitMQ의 메시지 전달 모델은 게시자(Publisher)가 큐(Queue)로 직접 메시지를 보내지 않고 **익스체인지(Exchange)**로 보냅니다.

- **익스체인지 (Exchange):** 메시지를 받아 어떤 큐로 보낼지 결정하는 우체국 같은 역할을 합니다.
    - **Direct:** 라우팅 키가 정확히 일치하는 큐로 전달.
    - **Topic:** 와일드카드(`#`, `*`) 패턴을 사용하여 유연하게 전달.
    - **Fanout:** 연결된 모든 큐에 메시지 복사본 전달 (브로드캐스트).
- **라우팅 키 (Routing Key):** 메시지에 붙는 '꼬리표' 혹은 '주소'입니다. Exchange는 이 키를 보고 어떤 큐(예: `penalty-queue`)에 넣을지 판단합니다.
- **이점:** 향후 알림 플랫폼이 추가되거나(예: 이메일, 카카오톡), 특정 알림만 다른 서버에서 처리하고 싶을 때 **코드 수정 없이** 설정만으로 확장 가능합니다.

## 4. 동기 vs 비동기: 지연 시간의 진실 (Latency Comparison)

벤치마크 테스트에서 두 방식 모두 **가상 지연 1초(Thread.sleep)**를 포함하고 있습니다. 하지만 결과는 판이하게 다릅니다.

| 비교 항목 | 동기 방식 (Synchronous) | 비동기 방식 (RabbitMQ - Asynchronous) |
| :--- | :--- | :--- |
| **UX (응답 속도)** | 느림 (외부 API 응답 대기 시간 포함) | **매우 빠름** (메시지 발행 후 즉시 반환) |
| **처리 시점** | 요청 시 즉시 처리 및 대기 | 요청 시 발행 후 **백그라운드에서 별도 처리** |
| **장애 격리** | 외부 서버 장애가 우리 서비스에 전파됨 | **강력한 격리** (외부 서버 장애와 무관하게 동작) |
| **확장성** | 트래픽 증가 시 API 서버 부하 급증 | **조절 가능** (컨슈머 수를 조절하여 부하 제어) |
| **유연성** | 알림 수단 추가 시 코드 수정 및 배포 필요 | **높음** (설정만으로 새로운 플랫폼/큐 추가 가능) |
| **신뢰성** | 네트워크 오류 시 데이터 유실 가능성 높음 | **매우 높음** (큐에 저장 및 안정적인 재시도 지원) |

### 이 데이터가 의미하는 것
비동기 처리라고 해서 1초 걸리는 작업이 0.1초 만에 끝나는 '마법'이 일어나는 것은 아닙니다. 하지만 **"사용자가 그 1초를 기다리지 않고 다른 일을 할 수 있게 해주는 것"**이 비동기 처리의 진정한 가치입니다. 사용자는 즉시 입금 완료 화면을 보고, 알림은 1초 뒤에 백그라운드에서 조용히 전달됩니다.

## 5. 실전형 벤치마크 테스트 방법 (Swagger)

로그인 없이 다음 단계를 통해 직접 실습해 보실 수 있습니다.

1. **Swagger UI 접속:** `http://localhost:8080/swagger-ui.html`
2. **`웹훅 성능 벤치마크` 그룹 찾기**
3. **`GET /api/v1/benchmark/webhook/sync` 실행:**
    - 응답이 올 때까지 약 1초간 화면이 멈추는 것을 확인 (사용자 대기 발생).
4. **`GET /api/v1/benchmark/webhook/async` 실행:**
    - 응답이 **즉시** 반환되는 것을 확인.
    - **서버 로그 확인:** IDE 콘솔에서 `[Benchmark] 비동기 처리 지연 시뮬레이션 종료` 메시지가 응답 이후 약 1초 뒤에 찍히는 것을 확인.

> [!IMPORTANT]
> 이 테스트를 통해 **"전체 작업 시간은 동일(1초)해도, 사용자가 체감하는 대기 시간은 비동기 방식에서 획기적으로 줄어든다"**는 점을 확인할 수 있습니다.
